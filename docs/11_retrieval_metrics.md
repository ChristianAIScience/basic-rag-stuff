# 11. Retrieval Metrics: Hit@k and MRR

## What

The LLM judges (chapter 10) grade *answers*. Hit@k and MRR measure the step before: does the retriever
put the right chunk **near the top**? They need labelled data - questions whose correct chunk is known.
The project creates those labels automatically:

```
1. sample 10 random chunks from the database           (fixed seed -> always the same chunks)
2. an LLM writes 2 questions per chunk                  -> 20 questions
3. label: the chunk a question was written from is its "gold chunk"
4. every retrieval strategy searches for every question -> ranked chunk ids
5. compare the ranking with the gold chunk               -> Hit@1, Hit@3, Hit@5, MRR@5
```

## The metrics

For one question the retriever returns a ranked list, e.g. `[c7, c2, c9, c4, c1]`, and the gold chunk is `c2`:

| Metric | Definition | Here |
|---|---|---|
| **Hit@k** | 1 if the gold chunk is in the first *k* results, else 0 | Hit@1 = 0, Hit@3 = 1, Hit@5 = 1 |
| **Reciprocal rank** | 1 / position of the gold chunk (0 if not within the cutoff) | 1/2 = 0.5 |
| **MRR@k** | mean reciprocal rank over all questions | – |

Averaged over all questions, Hit@5 = 0.85 means: for 85 % of the questions the gold chunk was among the top 5.
MRR additionally rewards *how high* it is: rank 1 counts 1.0, rank 2 only 0.5, rank 3 0.33.
Both are computed by plain Python - exact, repeatable and free (no judge involved).

Why it matters: the RAG chain sends the top 4 chunks to the LLM. If Hit@4 is low, the answer cannot be good,
no matter how good the LLM is.

## Why generate questions with an LLM?

Writing questions by hand for many chunks is slow. A generator LLM writes them in seconds, and because each
question comes from one chunk, the label is known for free. The prompt asks for natural, specific questions
in the generator's own words, so keyword search does not get an unfair advantage from copied phrases.

**Limitations - read them before trusting the numbers:**
- Only one chunk counts as correct. If a neighbouring (overlapping) chunk also answers the question,
  the metric counts a miss - the numbers are a **lower bound**.
- Generated questions can be too easy or too vague. **Review `evaluation_data/retrieval_dataset.json`**
  and delete or fix bad questions - a few good questions are worth more than many bad ones.
- 20 questions are a smoke test: one question changes Hit@k by 0.05.
- The labels are chunk ids. Re-ingesting with another `CHUNK_SIZE` changes the ids; the evaluation then
  stops and asks you to generate the dataset again.

## The code

```python
def hit_at_k(ranked_ids: list[str], gold_id: str, k: int) -> float:
    return 1.0 if gold_id in ranked_ids[:k] else 0.0


def reciprocal_rank(ranked_ids: list[str], gold_id: str, k: int) -> float:
    top_k = ranked_ids[:k]
    return 1.0 / (top_k.index(gold_id) + 1) if gold_id in top_k else 0.0
```

| File | Role |
|---|---|
| `db/chunks.py` | `fetch_all_chunks()` - all chunks with their ids (one SQL query) |
| `evaluation/question_generation.py` | `sample_chunks()`, `generate_questions()`, save/load the dataset |
| `evaluation/retrieval_metrics.py` | `hit_at_k()`, `reciprocal_rank()`, `evaluate_retriever()` |
| `examples/generate_retrieval_dataset.py` | creates `evaluation_data/retrieval_dataset.json` |
| `examples/evaluate_retrieval.py` | prints Hit@1/3/5 and MRR@5 per retrieval strategy |

## How it connects

It evaluates the five strategies from chapter 3 on the same labelled questions. The metadata filter is
given the category of the gold chunk - an "oracle" that shows the best case of filtering, marked with `*`.
The answer-level judges of chapter 10 and these retrieval metrics complement each other:
low Hit@k points to the retriever, good Hit@k with bad answers points to the prompt or the LLM.

## Run

Needs a real `LLM_API_KEY` and data ingested **with real embeddings** (fake embeddings make the ranking random).

```bash
uv run python -m examples.generate_retrieval_dataset            # 10 LLM calls -> 20 labelled questions
# review evaluation_data/retrieval_dataset.json
uv run python -m examples.evaluate_retrieval
uv run python -m examples.evaluate_retrieval --details          # rank of the gold chunk per question
```

Options: `--chunks 10 --questions-per-chunk 2 --seed 42`. Keep the dataset file in git so every
evaluation uses the same questions.

## Expected output (shape - the numbers depend on your data and models)

```
20 questions from 10 labelled chunks (generated by gpt-5-mini, seed 42)

strategy                    Hit@1    Hit@3    Hit@5    MRR@5
similarity                   0.70     0.90     0.95     0.80
mmr                          0.70     0.85     0.90     0.78
score_threshold (0.4)        0.65     0.80     0.80     0.72
metadata_filter*             0.80     0.95     1.00     0.87
hybrid (RRF)                 0.75     0.90     0.95     0.83

* filter uses the known category of the gold chunk (upper bound for metadata filtering).
```

How to read it: if Hit@5 is much higher than Hit@1, the right chunk is found but ranked too low -
a reranker or MMR settings may help. If the score threshold loses hits, the threshold is too strict.
